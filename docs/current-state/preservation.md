# Feature preservation scenarios

These examples describe observable results for a replacement system. They preserve the questions users can answer and the evidence behind those answers. Exact source files, database structure, chart libraries, and screen layouts are replaceable.

The scenarios below record current behavior unless a row explicitly calls for an unresolved decision. They are not newly executed tests. [Feature IDs](features.md) connect each example to the inventory; [behavior](behavior.md) supplies detailed calculations.

## Numerical boundary examples

| Example | Current expected result |
| --- | --- |
| A six-installment purchase of ARS 100 per installment, imported from installment one | Billed view: 100 each observed cycle. Purchase commitment view: 600 once. A later ARS card payment does not add spending. |
| Same series first observed at installment three | Purchase commitment view: 400 once; earlier installments are outside imported evidence, rather than silently reconstructed. |
| ARS 1,000 purchase plus ARS −200 reversal | Net spending 800; habits count one positive purchase, not two visits. Merchant concentration can omit a merchant whose complete net is nonpositive. |
| ARS 1,000 at monthly MEP 1,000 plus native USD 5 | Ordinary nominal spending: ARS 1,000; USD report: USD 6; dedicated currency split in nominal pesos: ARS 1,000 plus ARS 5,000 in the USD-billed series, before any allocated tax. |
| ARS 1,000 purchase with IPC source 100 and base 120 | Real spending ARS 1,200. Refreshing the reporting base can change this restatement without changing source principal. |
| ARS 1,000 purchase and ARS 100 eligible issuer tax, no other purchases | Tax-excluded spending 1,000; allocated tax-inclusive spending 1,100. This allocation is a view, not a second 100 purchase. |
| Receipt gross 12,345 cents and discounts −345 cents | Printed net must equal 12,000 cents. A printed 12,001-cent total rejects, even if every other check passes. A wrong printed unit price alone can warn while totals pass. |
| Three-installment charge of 3,334 cents versus receipt total 10,000 cents | Difference of multiplied charge is 2 cents, within the 6-cent matching tolerance. Receipt admission itself still requires exact printed totals. |
| Two receipts each having the same sole candidate charge | Auto-link neither; keep human selection available. One-to-one uniqueness must hold even when sources arrive in different orders. |

## Current limitations requiring parity decisions

Do not convert these into silent redesigns or mandatory defects. Decide whether the replacement keeps report compatibility, corrects the behavior, or offers both with explicit labels:

1. Brand-based account identity, installment-series collisions, and fingerprints that omit statement/account context.
2. Partial-history “accrual,” cycle-month aggregation, and the “cash” label for billed spending.
3. Ordinary peso spending omits native USD; the currency-split USD path handles installment rows differently from the shared spending path.
4. Expected forecast excludes USD subscriptions; taxes and controls do not affect every forecast component uniformly; variable range is historical min/max, not statistical confidence.
5. Automatic relinking after a manual unlink, stored associations with no live charge after source correction, and local matching ambiguity rather than a global assignment algorithm.
6. Statement replacement, mutable naming/category/product decisions, and stale alert-review cleanup provide no complete immutable history.
7. Fixed 4.33 shopping multiplier, product-match completeness, per-field conversion rounding, and edits to product unit without quantity conversion.
8. Due-date payment assumptions, reference fallback, and coverage-based bank-limit gaps can change interpretation when data is incomplete.

## Agreed classification and accounting targets for the replacement

These examples apply the accepted account-design decisions to a future implementation. They are intentional target behavior, distinct from the current-code baseline above. Amounts are synthetic. Q25–Q31 settle posting validation, correction scope/dates, historical reporting, durable-purchase defaults, receipt-first recognition and repayment attribution; Q8 accepts the [installment policy](../accounting/installments.md). See [the decision record](accounting-questions.md) for remaining evidence and cutover prerequisites.

| Target | Example | Accepted result |
| --- | --- | --- |
| T01 Travel criterion | A meal or fuel purchase made while abroad; an ordinary online subscription billed in USD | The purchase abroad uses Travel; the subscription retains its regular account. Neither currency nor overseas processor alone decides physical purchase context. |
| T02 Linked credit | A Travel purchase is later partly refunded or receives a directly linked promotion | The credit follows the original Travel account as a distinct event; it is not a new purchase or automatic unrelated income. Source and posted correction history remain traceable. |
| T03 Domestic receipt allocation | A verified, linked domestic purchase totals 100: reviewed items allocate 70 to groceries, 20 to cleaning, 10 to pets | Account allocations total 100 for the same purchase. Spending does not become 200 by adding receipt plus card evidence, and the full 100 is not recognized against each installment. |
| T04 Missing receipt | A domestic supermarket purchase totals 80, with no reliable item breakdown | Show the amount and supermarket evidence in Unallocated purchases. Do not assume Groceries, hide the 80, or invent allocation percentages. |
| T05 Correct product evidence | A mathematically verified receipt has an item matched to the wrong canonical product | Arithmetic verification alone does not approve the product/account mapping; keep the identity discrepancy reviewable before using that match for allocation or price comparison. |
| T06 Validated automatic posting | Identity, financial nature and totals are established under the agreed accounting rules, but the purchase purpose lacks sufficient detail | Permit automatic posting with Unallocated classification where appropriate. Ambiguous financial nature, duplicate identity or conflicting totals remains in review; no missing history or funding account is invented. |
| T07 Scoped account correction | Correct one purchase, then optionally save a future rule or request a matching-history update | Only the selected purchase changes by default. Future-rule and historical bulk effects are explicit actions; posted changes retain reversal/replacement history. |
| T08 Historical analytics after correction | An old purchase of 80 was assigned to Groceries and is corrected to Household supplies | Historical spending charts remove the 80 from Groceries and include it in Household supplies for the purchase's analytical period. The total remains 80; original evidence, the earlier assignment and any posted-entry revisions remain inspectable. Q29 also preserves the original effective period for the correction; a separate “as originally reported” chart mode is not required. |
| T09 One installment purchase | An evidenced interest-free consumption purchase of 600 is billed in six installments of 100 | Record one expense of 600 and full principal once. Later billing moves principal from unbilled to billed liability without increasing expense or total debt. Reimports, linked receipts and allocations do not repeat the purchase. |
| T10 Billing versus repayment | After the first 100 is billed, the issuer reports a payment of 100; it is the only billed amount | Before payment, billed debt is 100 and unbilled principal 500. After payment, billed debt is 0 and unbilled principal stays 500. Use Q9 payment-source clearing until bank integration; do not infer per-purchase payment allocations in mixed balances. |
| T11 Separate financing costs | A purchase has an explicit interest charge of 10 and an estimate of later interest | Record the supported charge as financing cost, separate from purchase principal; a forecast alone creates no posting. Do not infer hidden interest from an assumed cash price or force unknown components. |
| T12 Incomplete installment history | The first imported appearance is installment three of six | Preserve missing-history limits. Use supported opening billed/unbilled obligations where reconstruction is insufficient; do not invent earlier expenses, purchases or payments. Later evidence must not duplicate opening debt. |
| T13 Ordinary durable purchase | An ordinary personal household appliance is acquired for 300 | Record the ordinary purchase expense when acquired by default; do not automatically introduce a capital asset or depreciation schedule. An explicitly identified supported asset/prepayment uses its appropriate treatment; ambiguous financial nature remains reviewable. |
| T14 Effective period and correction time | A January purchase is reclassified in March; a separate refund arrives in April | The correction's reversal/replacement affects the original January effective period, while the actual March correction time and all prior evidence/entries remain inspectable. The refund is a distinct April event. No initial period locks prevent the accepted correction. |
| T15 Receipt before statement | A verified receipt supports an acquired purchase of 120, payment method and specific card; the statement arrives later | Establish one purchase and supported card liability, retaining pending statement reconciliation. Infer no installment schedule from the amount. The statement confirms/enriches the same purchase and establishes billing without another expense. Without sufficient acquisition/payment/card facts, retain receipt analytics but keep posting in review. |
| T16 Repayment attribution | Known billed Food debt of 100 precedes billed Travel debt of 200; a payment of 150 has no issuer allocation | Disclose oldest-billed-first attribution: Food debt becomes 0 and Travel debt 150. Total billed debt becomes 150; expenses are unchanged, and unbilled principal is untouched without evidence. Explicit issuer allocations take precedence. Unsupported opening components remain unattributed, excess payments remain unapplied credits, and all components reconcile to the card balance. |
| T17 Bilingual accounting workflow | Switch English/Spanish while viewing a purchase, its card debt, review states and correction history | Built-in account/group labels and interface messages translate; native amounts, journal identities, balances, allocation order, effective/recorded dates, reporting settings and selected context remain unchanged. Original source text stays intact and source parsing is independent of interface language. |
| T18 Custom account/group name | Rename a built-in account to “Mi casa” and create a custom group “Viajes 2026”, then switch languages | Both custom names remain exactly as entered in either language. Other built-in names translate normally. No second account/group, missing-translation error, changed membership or posting is created; no external translation is invoked. |
| T19 Retained localized accounting message | Reopen the same retained reconciliation error in English and Spanish | Render the same stable code and structured values in the selected language, with matching placeholders and exact financial values. Preserve raw source excerpts and prior evidence separately; a language change neither loses the error nor rewrites its financial history. |

The normal web command is `npm test` from `web/`. The real receipt OCR suite is opt-in through `npm run test:receipts`, requires macOS/runtime/source fixtures, and is distinct from offline transcript replay. Backup tests use `python3 -m unittest discover -s scripts -p 'test_backup.py' -v` from repository root. None was run as part of this documentation-only change.

Unit tests alone do not establish upload error handling, navigation, responsive controls, chart interaction, or OCR success on new issuer/receipt layouts. Validate P01–P27 against an isolated copy of representative data before declaring a rewrite preserves behavior. Avoid testing imports, restores, or corrections against the only copy of personal data.
