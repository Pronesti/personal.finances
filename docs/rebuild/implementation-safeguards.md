# Required implementation safeguards

This document closes the six architecture review findings. It is part of the rebuild contract, not implemented application behavior. Read it together with [architecture.md](architecture.md), [architecture-contract.json](architecture-contract.json) and [isolation-fixtures.json](isolation-fixtures.json). Registration and production account provisioning remain outside scope.

## 1. Owner-qualified storage and recovery

The document root contains `ledgers/<ledger-uuid>/objects/<sha256>`. Pending transcripts use `ledgers/<ledger-uuid>/pending/<pending-id>/<sha256>`. A pending ID is server-generated or a validated stable internal reference, never a caller-controlled path. Roots are canonical, private and non-overlapping; directories start at 0700, files at 0600. Resolve and validate ledger scope before filesystem access; reject symlink traversal, absolute archive paths and `..` components.

An object's content digest is not its owner identity. The v2 backup manifest and target `backup_metadata` projection include `ledger_id`, `kind`, `reference_id`, `relative_path`, `sha256` and `bytes` for every retained reference. Their identity is `(ledger_id, kind, reference_id)`; the object path is ledger-qualified. Preserve each reference, including two owners referencing identical bytes. A view selecting only a global hash/path with `UNION` is insufficient. Pending transcript references retain their own owner, source/revision association and content digest. Deduplicating archive payload bytes is optional, but never collapses logical references or restored owner namespaces.

The historical single-user view and `scripts/accounting_backup.py` are not compatible with this target unchanged: global `objects/`/`pending/` paths, hash-only metadata and an unrestricted whole-database dump must be replaced. Keep the original SQL in the historical context as source evidence; do not copy its recovery assumptions into the target.

Define administrator recovery format `tarjetas-owned-recovery-v2` with a coherent, writer-frozen capture of:

- All financial tables, immutable evidence and the owner-qualified reference inventory, including pending/rejected evidence. Record schema/application revisions and full-row identity/digest inventories.
- A separate protected identity component containing existing users, their password hashes, immutable ledger UUIDs and user-to-ledger mappings. Password hashes are sensitive recovery data: restrict access and encrypt this component with an operator-supplied recovery key kept outside the archive. The financial component remains protected administrator data. Encryption keys, APP_KEY, provider/database credentials and plaintext passwords are never included.
- Reference files plus their digests, an explicit allowlist of restored tables, and externally retained archive SHA-256. Do not automatically include every new platform table in the next backup. The platform identity relations and financial tables must restore together with their cross-schema FKs satisfied before access resumes.

Exclude sessions, personal access tokens, password-reset tokens and other temporary authentication state. On restore, start with an empty session store, clear persistent remember-login tokens and rotate any retained authentication recovery tokens before opening traffic. This invalidation applies even if the restored APP_KEY is unchanged. Existing accounts can then log in with recovered password hashes; creating accounts remains outside scope. If the protected identity component is unavailable, halt the restore for an explicit identity recovery/mapping decision; never silently attach historical ledgers to another user.

Restore only to an explicitly selected empty disposable target and new private roots. Validate the external archive digest, archive paths, format, revisions, all reference ownership, hashes and sizes before admission; verify schema/FKs/guards and full-row/object inventories before enabling access. Refuse nonempty targets and malformed/swapped/missing/corrupt references. Failed restore must not affect the source installation; partially restored targets remain quarantined. Treat restore as an administrator operation, with no ordinary-user endpoint. A user export contains only that ledger's financial rows and referenced bytes, omits all authentication data and is not a complete administrator recovery bundle.

The synthetic fixture has four immutable object references and four pending references. One PDF and one transcript have equal bytes in both ledgers, while each ledger also has exclusive content. Recovery must preserve all eight references and all eight owner-qualified paths, not merely six distinct digests. Compare both owners' inventories and amounts after relocation. Test deleting one shared-owner reference while keeping its twin, swapping owner metadata, corrupting bytes and replaying a pre-backup session. Each must fail its relevant integrity/authentication check; a newly authenticated owner still sees only its own ledger.

## 2. ORM mapping and distinguishable isolation tests

Use globally unique `row_id` UUID primary keys for Eloquent-managed financial records. Configure the model's primary key, key type and non-incrementing behavior explicitly. Preserve baseline logical `id` values and `UNIQUE (ledger_id, id)` for accounts and other ledger-local identities. References using logical IDs have composite FKs `(ledger_id, account_id)` to `(ledger_id, id)`. References using surrogate IDs likewise carry `ledger_id` and reference a unique `(ledger_id, row_id)` pair. Index FK lookup paths. Eloquent has no native composite-primary-key support; join tables with physical composite keys require explicit ledger-aware repository queries. [Eloquent primary keys](https://laravel.com/framework/docs/13.x/eloquent#primary-keys).

Resolve route binding inside the authenticated ledger. Do not use unscoped `find(logicalId)`, implicit global bindings, or default saves that mistake a logical `id` for a global primary key. Reads, updates, deletes, relations, locks and command lookups must carry the resolved ledger; deny owner changes after creation. Global scopes can help but do not replace explicit repositories/policies and composite database constraints. Background work must supply a verified owner context; missing context fails closed.

Run the original financial suite independently in each ledger, without changing its expected results. Then run the separate ownership fixture in a fresh scenario. It deliberately reuses logical purchase/account/command keys while assigning unequal native amounts and unique merchant labels. It also contains A-only and B-only IDs and document hashes. The fixture's markers name acceptance observations, not new production database columns. Seed through validated domain/factory adapters, map generated surrogate IDs, and do not bypass financial guards.

For a colliding key present in both ledgers, A gets A's resource and B gets B's resource. For an exclusively B-owned key, A gets 404, and vice versa. A shared hash may legitimately return identical bytes to either authorized owner; also inspect owner-qualified resolution through an internal test seam and each owner's distinct reference/financial metadata. Equal response bytes alone cannot prove authorization. Lists and reports must match each owner's exact sentinel set and native amount sum: A = 12,200 ARS cents; B = 23,200 ARS cents, never the combined 35,400. These two purchases per owner have no tax, repayments or FX in this isolated scenario. Updating A's shared-key resource leaves B unchanged; an attempted cross-owner relational link fails in PostgreSQL without partial writes. Forged owner fields never select another ledger; reject conflicting fields. The expected matrix, mutation outcomes and recovery paths are executable inputs for the future adapter, not proof that those features already work.

The database oracle is separate from request authorization. `isolation-fixtures.json` now declares ledger A and B copies of the shared pantry account, plus `expense:synthetic:b-only` exclusively in B. In the guarded disposable PostgreSQL target, insert an otherwise-valid `accounting.account_name_revisions` row whose actual FK columns are `(ledger_id=A, account_id=expense:synthetic:b-only)`. The parent tuple `(A, exclusive-key)` is absent while `(B, exclusive-key)` exists. Require **SQLSTATE `23503`**, the intended same-ledger account FK, and unchanged row/state digests after rollback. An API/ORM rejection, unrelated constraint failure or synthetic replacement table is not proof. Use fresh valid revision IDs/other required fields, force deferred constraints before observing the result, and keep all guards enabled. Test savepoints isolate each case. The fixture's account rows supplement the per-owner baseline chart only in this separate scenario; the B-only account has no postings and does not change financial totals. [PostgreSQL error codes](https://www.postgresql.org/docs/18/errcodes-appendix.html).

Keep three successful raw-database controls: A/shared pantry resolves to A; B/shared pantry resolves to B; B/exclusive account is valid. Roll each back so the named mutation/report scenario remains unchanged. A separate forged-owner HTTP case sends B's owner field while authenticated as A and expects HTTP 400 `owner_scope_conflict` with no writes. Reject that conflicting field before any owner selection; do not count it as a foreign-key test. The static checker derives tuple membership from declared accounts and rejects a supposedly negative case that would actually satisfy the FK. Actual PostgreSQL enforcement remains an implementation acceptance test.

## 3. Stateless public health

`GET /api/v1/health` returns exactly HTTP 200 and `{"status":"ok","service":"tarjetas-api","api_version":"v1"}` without reading PostgreSQL, private storage or the session. Exclude `EnsureFrontendRequestsAreStateful` on this route even when the rest of the API group uses `statefulApi()`. Do not attach `web`, `StartSession`, `auth:sanctum`, the ledger resolver, database-backed throttling or database-dependent service-provider boot work to this liveness path. Keep global CORS handling; OPTIONS must be stateless too. Sanctum otherwise starts session middleware for recognized SPA origins, including guest requests. [Sanctum middleware](https://github.com/laravel/sanctum/blob/4.x/src/Http/Middleware/EnsureFrontendRequestsAreStateful.php).

The login screen uses the public client with credentials and XSRF disabled. Browser tests use the real configured SPA Origin/Referer, first without cookies and then with existing session cookies via a deliberately credentialed probe. Both return the same liveness response without `Set-Cookie` or session-table changes. Repeat GET and preflight with PostgreSQL unavailable: liveness still succeeds and the frontend can read the CORS response. Inspect the resolved route middleware stack. A curl without SPA headers does not prove this property. Health means API process reachability, not financial/database/OCR readiness; do not advertise it as readiness.

## 4. Original document button and session behavior

The original-PDF action must use the SPA's configured credentialed HTTP client to fetch `/api/v1/documents/{hash}` as a blob, after resolving authorization on the server. Do not navigate a new tab directly to the raw API URL: a top-level request with no Origin/Referer can miss Sanctum's stateful session middleware. Never add a bearer token, browser-stored credential, hash-only public route or unbounded signed-link bypass to compensate.

On the user's click, synchronously reserve a blank same-origin viewer tab and immediately set its `opener` to null. Fetch with `withCredentials: true`, `responseType: 'blob'`, the client's default `Accept: application/json` and the trusted base URL. The document action explicitly streams its authorized media type on success and returns JSON on errors; blob response handling must decode JSON error blobs without treating them as documents. Check status and allowed content type before creating an object URL. Navigate the reserved tab to that blob only on success. If popups are blocked, show a visible second-click Open/Download link to the fetched blob. Close an unused reserved tab on failure; show 404 as unavailable and route 401 to the existing session-expiry/login flow while clearing private caches. Never display an error JSON/HTML body as a PDF. Do not automatically retry a financial mutation during session recovery.

Retain object URLs only while the authorized viewer/download is usable, then revoke them and release blob references on viewer closure, replacement, component cleanup or logout. Closing the tab is part of expiry/logout cleanup for app-controlled viewers; already downloaded bytes cannot be remotely revoked. Blob creation itself does not require widening the API's CORS allowlist. Configure the SPA's viewer/CSP policy deliberately and verify it in the supported browsers.

Browser acceptance clicks the actual button after login, opens the expected PDF bytes, checks the popup-blocked fallback, rejects an exclusively other-owner hash, handles an expired session, and confirms a shared hash resolves through the caller's reference. Server tests verify hash/size, private/no-store and nosniff headers and safe content disposition. A direct authenticated test-client GET alone is insufficient proof of the button flow.

## 5. Disposable PostgreSQL verification targets

The plan examples `backend.testing.env.example` and `backend.browser-testing.env.example` describe separate databases, roles, cookie domains and roots. They contain no real credentials or target authorization. Copy them to the implemented backend's appropriate environment files only after explicitly selecting disposable targets. Never load the current installation's `.env`, reuse its PostgreSQL role or borrow its private roots for tests.

Use disjoint environment cookie parents, with the SPA and API sharing a parent **within** each environment:

| Environment | SPA origin | API origin | Cookie parent |
| --- | --- | --- | --- |
| Development | `https://app.tarjetas.test` | `https://api.tarjetas.test` | `.tarjetas.test` |
| Integration | `https://app.tarjetas-integration.test` | `https://api.tarjetas-integration.test` | `.tarjetas-integration.test` |
| Browser acceptance | `https://app.tarjetas-browser.test` | `https://api.tarjetas-browser.test` | `.tarjetas-browser.test` |

These remain examples requiring normal Lerd/DNS/TLS discovery and configuration; no domains are provisioned by this specification. Keep distinct session-cookie names as well. Laravel's `XSRF-TOKEN` name is shared by convention, so different session names alone do not prevent cross-environment XSRF collisions. No environment's cookie domain may domain-match another environment's SPA/API host; also reject equal or ancestor/descendant cookie parents. Apply hostname-label domain matching, not a raw string suffix. In one browser profile, bootstrap development then browser acceptance (and reverse order), verify exactly the intended XSRF cookie is visible in each SPA, check request cookie headers for absence of foreign environment cookies, and perform valid CSRF mutations without 419 failures. No weakening of CSRF/CORS is permitted to pass this check. [Cookie domain matching](https://www.rfc-editor.org/rfc/rfc6265#section-5.1.3).

Remove/override scaffold `phpunit.xml` settings that force SQLite `:memory:` or array sessions. Integration tests require PostgreSQL; session/browser tests require the database session driver. Pure domain tests may avoid the database, but cannot count as PostgreSQL or browser proof. Laravel's standard test mode may bypass CSRF, so the real browser server uses `APP_ENV=browser-testing` with actual CSRF/session middleware enabled, dedicated test credentials, and no testing-only CSRF exception. [Laravel testing environments](https://laravel.com/framework/docs/13.x/testing).

Implement a fail-closed guard **before** migrations, `RefreshDatabase`, schema drops, transactions that initialize schema, or test server bootstrap can mutate anything. It must inspect the final resolved connection/configuration, not merely the environment file:

1. Reject cached application configuration for destructive test runs and unexpected connections, drivers or environment names. Require an independently maintained, explicitly approved local allowlist of test server/database/role identities and canonical storage roots. An empty allowlist denies access. A database-name suffix or `APP_ENV=testing` alone is insufficient.
2. Connect read-only to validate `current_database()`, `current_user`, server identity and an operator-created marker UUID in a protected `test_safety` schema. The marker must match the approved target and environment. Keep that schema out of destructive schema lists/search paths; the test role cannot create/change its marker. The role must have no access to development/production databases, no superuser/createdb/createrole privileges and no ability to alter the approved-target registry.
3. Match separate, canonical disposable document/reference/temp roots to the approved target. Refuse overlap with each other or any live/development root, symlink escapes and unspecified paths. Never apply a test purge to unverified roots. Redact credentials in failures.
4. Every destructive command and early test bootstrap invokes the same guard independently; skipping a convenience preflight cannot bypass it. Parallel workers require separately approved targets and markers. Production/ordinary development startup must not enable fixture endpoints or test bypasses.

Planned integration sequence, from the implemented `backend/`, after configuration and target approval:

```sh
lerd php artisan tarjetas:test-target:check --env=testing
lerd php artisan test --env=testing
```

These commands are a requirement to implement, not available commands in today's repository. The test bootstrap repeats the guard before any destructive hooks. Browser setup runs the equivalent guard with `--env=browser-testing` before migrations/seeding/server startup, and serves the separate test API/SPA origins. Use synthetic factory users only. Verify the guard refuses: a live/development database, the wrong role/marker, cached dev config, a forced SQLite connection, overlapping/private source roots, and an unapproved parallel-worker database. No destructive SQL or file deletion may occur in those negative cases. Document the actual discovered Lerd configuration rather than assuming example database hosts resolve inside its runtime.

## 6. Upload size and processing budgets through production HTTP

Preserve per-file maxima exactly: statements **10 MiB = 10,485,760 bytes**, receipts **40 MiB = 41,943,040 bytes**. Equal-to-limit is admitted for parsing; plus one byte produces the domain `too_large` HTTP 400 response before processing. Parsing can still reject an invalid supported-size file. Preserve structured receipt verification errors and retained correction evidence.

Use these initial deployment ceilings, record effective values, and map application settings explicitly:

| Layer | Required initial setting |
| --- | --- |
| Application | Statement/receipt limits above; single file; at most 1 MiB of multipart framing/non-file fields. Enforce bounded field/count sizes. |
| PHP-FPM | `file_uploads=On`, `upload_max_filesize=40M`, `post_max_size=48M`, `max_file_uploads=1`, `max_input_time=120`, `max_execution_time=720`. Verify FPM values, not just CLI php.ini. |
| Nginx/API ingress | `client_max_body_size 48m`; `client_body_timeout 120s` (an inactivity timeout, not a total upload deadline). Bound edge upload time to 180 seconds. |
| Application processing | Overall monotonic request wall-clock deadline 720 seconds including intake; up to three OCR attempts, each at most 180 seconds and capped by remaining budget. Intake/admission/rendering/verification/persistence together have a 180-second allowance; every stage is also capped by remaining request time. |
| FPM termination | `request_terminate_timeout=750s` is an emergency FPM-local ceiling, not the ingress total deadline; propagate the earlier trusted deadline. |
| Nginx FastCGI/upstream | `fastcgi_read_timeout 780s` or corresponding proxy read timeout for the actual serving model. |
| Outer ingress/client | Enforce an independent 720-second total request timer at the first trusted ingress. Transport read/response waits may allow 800 seconds; they never extend that total. SPA import timeout is 1,000,000 ms as a network fallback. General short API requests keep shorter timeouts. |

### Authoritative deadline before buffering

Default Nginx `fastcgi_request_buffering on` reads the request body before handing it to FPM. PHP request entry, an FPM timer and a later `$msec` evaluation therefore cannot establish when the client upload began. The required deadline starts when the **first trusted ingress receives the first request byte**, before any body buffering. It covers upload, every ingress/upstream queue, rendering, OCR, database work and response preparation. [Nginx request buffering](https://nginx.org/en/docs/http/ngx_http_fastcgi_module.html#fastcgi_request_buffering).

The deployment must implement this protocol, not infer it from idle/read timeout settings:

1. The first trusted ingress records a per-request monotonic start and simultaneously a Unix-millisecond start stamp. It sets a fixed deadline `started_at_unix_ms + 720000` and enforces its own monotonic 720-second total timer and separate 180-second total upload timer. It also enforces the cumulative non-OCR allowance before backend admission: before any OCR starts, all upload and upstream/FPM queue time consumes that allowance. With 120 seconds uploaded, only 60 seconds of non-OCR queue/admission time remains. A request still waiting at 180 seconds is cancelled there, not left queued until 720 seconds. Dispatch/connection wait limits and the backend admission guard must preserve this bound. Transport read/inactivity timers reset none of these budgets.
2. Discard all client-supplied request-start/deadline values, including duplicate/alternative header spellings. At backend dispatch, provide a server-issued request ID, original start and fixed deadline through protected FastCGI parameters (`TARJETAS_INGRESS_REQUEST_ID`, `TARJETAS_INGRESS_STARTED_AT_UNIX_MS`, `TARJETAS_INGRESS_DEADLINE_UNIX_MS`) or an authenticated private-hop equivalent. These are per-request trusted server metadata, not `.env` variables and not automatically trusted `HTTP_*` headers. The origin must be reachable only through this trusted path. Every subsequent proxy/private macOS processing hop preserves the same deadline and owner context; it may shorten a budget, never issue a later deadline.
3. Before intake admission, processing or writes, backend middleware validates the trusted channel, metadata format/request association, exact `deadline = start + 720000`, and bounded clock synchronization. A missing/invalid stamp or unhealthy clock fails closed with HTTP 503 `deadline_metadata_invalid` before work; an expired valid deadline returns 504 `processing_timeout`. Require clock skew no greater than 1,000 ms across the private execution path. Compute `remaining = trusted_deadline - local_unix_now - 1000` and immediately turn this conservative remaining allowance into a local monotonic deadline. Never restart 720 seconds on PHP entry, each OCR attempt or a retry/correction inside that request. A separate HTTP correction request gets its own ingress-issued request context; it does not reuse the original document upload's deadline. Local wall-clock changes cannot extend the monotonic allowance. Each private hop recomputes conservatively and caps it by its caller's remaining allowance.
4. Cap each OCR attempt at `min(180000 ms, remaining)` and at most three attempts. Maintain one cumulative, monotonic non-OCR counter for upload, every queue/admission wait, rendering, verification, persistence preparation and cleanup. Pause that counter only for actual active OCR execution; parent/network/private-worker queue wait is not OCR. On handoff, carry the server-owned cumulative phase context and remaining allowance over the trusted private path, charge transit/queue time, and never reset the counter between attempts or hops. Apply conservative clock conversion when crossing clock domains; uncertainty can shorten but cannot enlarge the remaining allowance. Cap each non-OCR phase at the smaller of its remaining cumulative allowance and original request time. Reserve and charge cleanup before admitting the fixture's financial command. Kill/reap processing groups and cancel upstream work on expiry or ingress cancellation; bound database statements/locks by remaining time and roll back interrupted transactions. Reconcile an ambiguous completed atomic commit with the original idempotency key, never a second posting. The ingress's total timer still closes a stuck request by 720 seconds; closing the connection alone does not prove downstream work was cancelled.
5. Keep health outside this processing middleware. Record the actual ingress hook/timer implementation, protected metadata mapping, clock-health check, private-hop cancellation and effective FPM/proxy settings as deployment artifacts. Plain Nginx read timeouts, a static `fastcgi_param` assigned at dispatch or `fastcgi_request_buffering off` alone do not implement this protocol. If the chosen ingress lacks a before-buffering start hook/total timer, provide a verified ingress adapter before claiming synchronous import readiness; do not deploy with an inferred PHP start time.

### Composed phase-budget acceptance

`deadline-fixtures.json` separates **normal** acceptance from the **outer-watchdog fault injection** and independent upload-boundary controls for that isolated harness. Normal cases enforce every production limit. Each `processing_phases` entry identifies active OCR (with an attempt number) or non-OCR work and a deterministic duration. `requested_processing_ms` must equal their sum. `cleanup_ms` is additional precommit non-OCR work, not free time after the budget. The synthetic adapter admits its one atomic financial command only when every required phase completes within the limits. Retaining immutable pending evidence is separate from posting money.

The elapsed-time oracle reports both wall time and cumulative non-OCR consumption. For example, 120 seconds of upload plus 10 seconds of queue leaves 50 seconds of non-OCR allowance, alongside 590 seconds of raw request time (589 after the clock margin). A valid 640-second path spends 480 seconds in active OCR and 160 seconds in non-OCR phases. It succeeds. Uploading for 120 seconds and then queueing for 61 seconds must instead terminate **at 180 seconds**, before backend admission, with HTTP 504 `non_ocr_budget_exceeded` and zero financial postings. After actual OCR, the same cumulative allowance resumes: the verification and cleanup fixtures prove it is not reset or silently omitted.

For deterministic boundary cases, expiry wins a tie. No phase or backend admission starts with an exhausted allowance; completion at the expiry boundary is rejected. The final upload byte must arrive strictly before 180,000 ms. At or after 180,000 ms, including exact completion at the deadline, the independent upload guard reports HTTP 408 `upload_timeout` before backend admission, ahead of the equal non-OCR edge limit. This applies in both normal and isolated-test modes; disabling the non-OCR guard never disables upload expiry. Otherwise an exhausted non-OCR allowance reports 504 `non_ocr_budget_exceeded`; the original request guard reports 504 `processing_timeout`, and an individual OCR attempt reports 504 `ocr_attempt_timeout`. When active-phase timers coincide, use original-request, then non-OCR, then OCR-attempt diagnostic priority. Normal phases do not acquire more time from any later timer. The clock-synchronized arithmetic uses exact milliseconds; actual multi-host implementations may end earlier when conservatively accounting for clock uncertainty and must never exceed these limits.

The ordinary long-queue fixture now stops at the earlier 180-second budget. A separate `outer_watchdog_queue_timeout_fault_injection` deliberately disables only the non-OCR guard in an isolated test harness, allowing the trusted outer watchdog to be observed at 720 seconds without dispatching backend work or posting money. The harness also checks upload completion at 179,999, 180,000 and 180,001 ms: the below-limit upload reaches backend admission, while exact/above-limit uploads stop at 180,000 ms with HTTP 408, no backend start and zero postings in both modes. In normal mode the 1 ms of work after the 179,999 ms upload then exhausts the separate non-OCR budget; the isolated mode permits that work because only that budget is disabled. The `mode` and `fault_injection` fields describe harness scenarios; they are **not request fields, environment switches or production bypasses**. Ordinary clients cannot select the mode or disable any guard. The isolated 720-second expectation must never be copied into normal HTTP acceptance. Real wire tests must record which scenario is normal and which is injected; run all ordinary guards for the normal cases, and prove the outer timer still works when that specific inner guard is faulted.

The normal processing-timeout fixture still proves the original request deadline independently binds after three bounded OCR attempts, before the non-OCR allowance is exhausted. Forged client stamps cannot extend either budget. Missing/invalid trusted metadata fails before work. These remain static arithmetic oracles; implementation must verify actual buffering, stage accounting, admission cancellation and process cleanup.

PHP's execution limit alone does not reliably bound child-process/IO wall time. Bound rendering memory/pixels, temp-disk and concurrent jobs as well; document measured finite budgets for the supported macOS adapter before claiming OCR readiness. A file-size limit alone does not bound raster memory. [PHP input and upload configuration](https://www.php.net/manual/en/ini.core.php), [Nginx body limits](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size), [Nginx FastCGI timeouts](https://nginx.org/en/docs/http/ngx_http_fastcgi_module.html#fastcgi_read_timeout).

An ingress with a shorter hard response ceiling cannot support this synchronous processing contract unchanged. Resolve that hosting mismatch before deployment; silently switching imports to asynchronous semantics would change the API contract. Return a structured processing-timeout error when the application controls the failure; handle upstream 413/504 and non-JSON errors in the SPA. Oversized whole request bodies return 413. Map PHP `UPLOAD_ERR_INI_SIZE` for an oversized individual file to the same per-file HTTP 400 `too_large` response; map `post_max_size` body rejection to 413. Distinguish either from a genuinely missing file. A timeout must not produce partial financial postings. Retained immutable pending evidence is allowed and must remain owner-scoped. Ambiguous network failure after an atomic commit requires reconciliation/replay with the original idempotency key, not a second posting.

Verify all limits through the actual browser/API ingress/FPM path, not only a request fake or CLI: valid padded synthetic PDFs at exactly each file maximum, maximum plus one, legal multipart overhead, oversized bodies, parser rejection, and bounded slow processing. Use safe PDF trailing comments to reach sizes without private data. With request buffering enabled, exercise a throttled upload plus queue delay plus a slow processing stub in the same request; measure from first ingress byte, assert original deadline metadata at backend/private worker, verify cancellation/process cleanup and unchanged state, and repeat with forged client stamps. Missing/extended trusted stamps must fail before work. Repeat with normal processing across the separate test origins. Inspect effective headers/params and timers rather than asserting elapsed arithmetic alone. A slow synthetic worker must prove the effective timeout/error/cleanup path, and a successful import taking more than a default 60-second proxy timeout must survive. Verify the deadline with controlled clocks/short budgets in focused tests and the deployed stack with a bounded slow-worker smoke. Record actual effective FPM/proxy/edge values and verify no partial postings. Do not claim these runtime checks passed during this documentation revision.
