# Tarjetas API

Independent Laravel 13 / Sanctum JSON application. Run PHP and Composer using this machine's `~/.config/agent-skills/runtime.md`. The PHP framework/auth/health/native inspection artifact has no frontend build, Next.js or application-screen dependency. Receipt extraction and read-only analytical projections additionally use the independently built private Node 24 helper; local Vision OCR requires the supported private macOS/Python boundary.

The committed rebuild contract starts at `../docs/rebuild/START-HERE.md`. `openapi.json` describes the implemented versioned contracts. The public surface covers sessions, retained documents, native accounting/source inspection and receipt intake/correction/product review/reconciliation. Receipt intake requires authenticated trusted-ingress deadlines and fails closed when that boundary is absent. Statement intake/history and explicit historical receipt associations/full refunds are exposed through versioned contracts. Owner-scoped analytical report projections and persistent alert annotations are implemented; account/group naming, product rules/rematching, merchant selected/future/confirmed-history classification and historical source-only classification are available. Optional external proposals and remaining acceptance details are still pending. See `ingress/README.md` for local-only ingress acceptance and its production limitations. Existing accounts and their private ledger must already exist; public registration and production provisioning are outside scope.

## Installation

From this directory, `composer install` installs the lockfile. Configure a private `.env` using `.env.example`, generate a new application key only for a new installation, and run explicitly targeted PostgreSQL migrations. Health is public/stateless and needs neither a database nor an application key. Session/financial requests need PostgreSQL and an application key. There is no SQLite connection or fallback. Never copy an existing installation's environment into test configuration.

The browser SPA talks directly to the API origin. CORS accepts only the configured complete origins; Sanctum stateful hosts have no schemes. Session cookies use the configured shared parent, Secure, HttpOnly and SameSite=Lax; XSRF-TOKEN is deliberately readable. Give every environment a disjoint cookie parent and separate session name. All API paths are `/api/v1/*` except Sanctum's `/sanctum/csrf-cookie`. Unknown API paths return JSON 404.

## Guarded acceptance

`.env.testing.example` and `.env.browser-testing.example` are templates, not target approval. The operator independently creates disposable databases/restricted roles and a protected `test_safety.target(marker uuid, environment text)` row. The database has an operator-selected `cluster_name`. The test role must not own the database, be privileged, inherit roles, mutate the marker or connect to another non-template database.

The operator maintains a read-only local JSON registry outside the checkout:

```json
{"targets":{"operator-selected-id":{"approved":true,"environment":"testing","host":"127.0.0.1","port":55451,"database":"operator-selected-disposable-db","role":"restricted-test-role","server_id":"operator-selected-cluster-name","marker":"operator-selected-uuid","roots":{"documents":"/absolute/private/documents","references":"/absolute/private/references","temp":"/absolute/private/temp"},"protected_roots":["/absolute/live-root"]}}}
```

Set `TARJETAS_TEST_TARGET_ID` and `TARJETAS_TEST_TARGET_REGISTRY`; use absolute canonical, non-symlink, writable roots with no group/other permissions. All three roots must be disjoint, including against protected live roots. The registry must have no write permission bits (e.g. 0400). Blank/mismatching configuration denies access. The guard uses final resolved connection settings and a read-only PostgreSQL identity/marker/privilege probe. It never initializes schema or repairs targets.

Run `php artisan tarjetas:test-target:check --env=testing`, then `php artisan migrate --env=testing`, then `php vendor/bin/phpunit`. PHPUnit's early bootstrap and PostgreSQL base case repeat the guard before hooks. Migration/destructive Artisan commands and test HTTP middleware independently enforce the boundary. Pure unit tests can run without a database via `php vendor/bin/phpunit --testsuite=Unit`; the stateless health feature file also needs no database. Financial feature tests inherit the PostgreSQL guard and require an approved target. Stateless health remains outside test HTTP checks so it can prove liveness when PostgreSQL is unreachable.

Browser acceptance uses the separately approved browser environment, real CSRF middleware (`APP_ENV=browser-testing`), database sessions and synthetic factories. After the guard/migrations, `php artisan db:seed --env=browser-testing` creates only the two synthetic acceptance users and owner-qualified fixture document references. The synthetic password appears in the test code and is never intended for ordinary accounts. Seeding directly repeats the guard. Re-running it verifies existing owner mappings and object bytes. Immutable objects may remain if a SQL transaction rolls back; no filesystem transaction is claimed.

Run the test API with `php artisan serve --env=browser-testing --host=127.0.0.1 --port=8191 --no-reload`, proxy it through the approved HTTPS API `.test` host, and start the separate SPA. `artisan serve` is for local acceptance only. The deployment still requires actual FPM/ingress settings, protected deadline transport, private processing readiness, and separately authorized production smoke/recovery.

## Private analytical build

From `backend/`, run `npm ci --prefix processing` and `npm run build --prefix processing`. This build reads only backend-owned source and emits self-contained private helper bundles. It never reads `web/`, `frontend/`, browser storage or database credentials. Laravel supplies owner-qualified snapshots and validated references via stdin. See `processing/src/reporting/README.md` for the guarded PHP fixture adapter and comparison command. This is separate from PostgreSQL/API/browser and production hosting acceptance.

## Owner-aware local recovery and exports

The guarded `tarjetas:recovery` operator implements `tarjetas-owned-recovery-v2`. It is an administrator tool with no user-facing restore endpoint. It freezes database writers with table locks and an exported PostgreSQL snapshot, captures only the explicit platform/financial table allowlist, encrypts users/password hashes/immutable ledger mappings using AES-256-GCM, and retains owner-qualified object/pending references, global reference files, per-table digests and separate full-row identity/digest inventories. Keys, APP_KEY, credentials, application code, sessions, password-reset state, queues and caches are excluded from archive payload data. Restored remember tokens are cleared. Equal content hashes never collapse owner/reference identities. `accounting.backup_metadata` exposes the owner-qualified persisted reference projection.

Use an operator-supplied private file containing exactly 32 random bytes, kept separately from the archive, and an explicit canonical matching-major PostgreSQL binary directory. The system-default PostgreSQL tools may belong to another major. Store the externally retained ZIP SHA-256 outside the archive. All paths/roots must be canonical/private and the output must be a new file. Examples, from `backend/`:

```sh
php artisan tarjetas:test-target:check --env=testing
php artisan tarjetas:recovery capture /absolute/private/capture.zip --key-file=/absolute/separate/key --pg-bin=/absolute/postgresql/bin --env=testing
php artisan tarjetas:recovery inspect /absolute/private/capture.zip --sha256=EXTERNALLY_RETAINED_SHA256 --key-file=/absolute/separate/key --env=testing
php artisan tarjetas:test-target:check --env=recovery-testing
php artisan tarjetas:recovery restore /absolute/private/capture.zip --sha256=EXTERNALLY_RETAINED_SHA256 --key-file=/absolute/separate/key --pg-bin=/absolute/postgresql/bin --env=recovery-testing
```

The extra recovery profile is not approval: its separately approved target/role/marker/roots must pass the same independent guard. Its environment may be `testing` while the explicitly selected file is `.env.recovery-testing`; direct server processes must receive all resolved profile settings rather than silently selecting another environment file. Configure the same explicit application build revision for capture/restore; local work in progress is stamped as such. Production operator authorization/configuration remains separate and hosting is deferred.

Restore validates archive SHA, paths, ownership, encrypted identity, all payload hashes/sizes and reference/row inventories before database admission. It requires an empty target and fresh document/reference roots. PostgreSQL pre-data, protected identity, financial data and post-data guards/constraints load together in one transaction; the existing bootstrap `public` schema entry is excluded from the restore list. Full rows, identities, references and bytes are checked before declaring the copy restored. Keep restored traffic quarantined until API/browser/native acceptance passes. A failed SQL load rolls back; later validation failures leave the target quarantined and never modify the source.

`reset-acceptance` exists only for the explicitly approved registry target named `recovery`. It repeats the guard and refuses any financial/identity/file difference from the supplied attestation archive before clearing that synthetic restored copy. It cannot reset integration/browser/production targets. It is a disposable acceptance hook, not rollback or a production reset command.

Ordinary owners can download `/api/v1/exports/ledger` from the accounting screen. Its ZIP contains only that owner's financial rows/documents and no authentication component. The server resolves the ledger, uses a private temporary file, returns private/no-store/nosniff headers and deletes the file after sending. `tarjetas:ledger-export LEDGER_UUID /absolute/private/export.zip` is its guarded local operator counterpart. Neither export is an administrator recovery archive.

`RecoveryArchiveTest` needs `TARJETAS_ACCEPTANCE_PG_BIN` set explicitly; it otherwise reports a skip. It executes actual capture/encryption/inventory, wrong key/SHA, swapped owner, missing owner reference, corrupted bytes/path and nonempty-target refusals. The separate browser recovery test requires the protected synthetic state generated by `tarjetas:acceptance:recovery-users` before capture and an independently built relocated SPA/API. It proves old database-session rejection (with a deliberately adapted cookie name and unchanged APP_KEY), recovered password login, owned native amounts/PDF bytes, viewer cleanup and disjoint-environment cookie coexistence. No cloud backup/PITR service is selected.


## Portable synthetic reconstruction and local release checks

`php artisan tarjetas:reconstruct /approved/private/temp/corpus/manifest.json --ledger=FACTORY_LEDGER_UUID --env=testing` requires an explicit existing fresh factory ledger and approved target/private roots. It reads only an extracted synthetic portable corpus under that target's temp root; it never opens `web/`, a live SQLite installation or another project. Supported manifest format is `tarjetas-portable-synthetic-v1`: `mode` (`historical` or `opening`), `cutoffDate`, explicit `cards`, immutable original `rows` (`table`, `sourceId`, `payload`), `objects` (`path`, `sha256`, `bytes`), `statements`, `openings`, and optional `expectedNative`. Object paths are relative to the manifest directory, canonical, bounded, hash/size checked and symlink/traversal refused. The full original manifest is retained too.

Each statement supplies `source: {table: "statements", sourceId}`, `cardId`, retained `pdfPath`/`jsonPath`, and explicit `lines: [{source: {table: "transactions", sourceId}, occurrence}]`. Exact printed monetary/date/identity fields must agree before line mapping. Historical mode uses ordinary admission; opening mode retains observations and requires explicit latest issuer balance proof. An opening supplies `statementSource`, `cardId`, native `currency`, `observationDate`, exact `billedMinor`/`unbilledMinor`, retained `supportingPaths` and `obligations`. Future schedules alone never prove principal. A supported obligation requires an exactly verified retained receipt, explicit funding confirmation, matching installment/date evidence and exact integer principal decomposition. `principalEvidence` contains retained `pdfPath`, `rowsPath`, `statementOccurrence`, `fundingConfirmed: true` and an optional retained receipt source mapping. Reusing one receipt for multiple obligations is refused. Uncertain/unsupported cases remain unresolved; opening books never imply complete historical coverage.

Owner-qualified immutable reconstruction runs, original row/object digests, ID mappings and reports participate in recovery/export. Original JSON object/array shapes and original migration records remain provenance distinct from Laravel migrations. The entire admission transaction rolls back for inconsistent mappings or unsupported proof. Content written before SQL admission may remain unreferenced, as with ordinary imports. A matching completed manifest/revision is idempotent; any other nonempty ledger is refused. Exact `expectedNative` maps `cardId/currency/accountId` to signed decimal integer strings, including zero accounts touched by journal lines. The report retains differences, unresolved operations and its supplied-corpus coverage scope; these are never waived to claim complete reconstruction.

`php artisan tarjetas:integrity LEDGER_UUID --env=testing` is read-only and owner-qualified. It checks journal balance, persisted object bytes, retained row digests, reference bindings, validated PostgreSQL constraints and reference readiness. `--release-check` also refuses open reviews and incomplete reconstruction. This is local financial admission evidence; separate build/browser/processing/recovery/deployment checks are still required. Neither command selects or provisions production accounts or hosting.

`php artisan tarjetas:references --env=testing` returns the current analytical fingerprint. Publish a complete local `{cpi, mep}` JSON using `tarjetas:references /absolute/private/input.json --expected-current=FINGERPRINT --env=testing`. The guarded operator never fetches a provider or sends financial data. It stages validated immutable IPC/MEP files and atomically switches one release manifest, retains source SHA/time, preserves old releases, refuses stale updates and reloads on the next read without a process cache. Native journals do not change.

Optional merchant proposals default to disabled. Their provider boundary accepts only sanitized names, validates all responses and requires human account/scope selection. `TARJETAS_PROPOSAL_DRIVER=synthetic-test` is a deterministic acceptance adapter that requires the independent disposable-target guard and synthetic names; it cannot operate in production. Its SPA notice identifies it explicitly. Historical-source proposals classify retained presentation without creating purchases. Rejections suppress sanitized names; a proposal cannot overwrite a conflicting owned rule. Merchant-family merges require the exact current family/fact preview and explicit confirmation.
